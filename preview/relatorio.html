Relatório de Experiência

AI-DLC na prática: redesign de frontend guiado por ciclo de vida agêntico

Projeto: sistema-condominio-qr · React 19 + Vite + Tailwind 4 + .NET 8 · AI-DLC 2.11.2 · Harness: Kiro IDE · 30/10/2026

1. O objetivo

Testar a metodologia AI-DLC (AI-Driven Development Life Cycle) da AWS em um caso real: o frontend do sistema de condomínios com QR Codes tinha um visual (dark roxo/ciano com glassmorphism) que não agradava. A meta era avaliar se um ciclo de vida estruturado para IA — com planejamento, gates humanos e auditoria — entrega um resultado melhor e mais controlado do que o uso ad-hoc de assistentes de código.

A tarefa concreta: redesign completo do visual mantendo React 19 + Tailwind 4 e toda a lógica de negócio, rotas, autenticação JWT e integração com a API .NET.

2. A jornada

2.1 Setup

  • Instalação via irm .../install.ps1 | iex. Adaptado para o Git Bash com funções irm/iex delegando ao PowerShell (descoberta: Git Bash carrega ~/.bash_profile, não ~/.bashrc).
  • aidlc config --harness kiro-ide gerou o harness .kiro/ (skills, agentes, hooks) e o workspace aidlc/ (memória, intents, auditoria). aidlc doctor: 51 checks OK, com aviso de caminho longo (101 + ~185 chars > limite de 260 do Windows).

2.2 Execução

  • Plano feature (33 estágios) escolhido entre 11 perfis; intent frontend-redesign criado.
  • Etapa de elaboração ("Mob Elaboration"): a IA fez 10 perguntas sobre negócio, usuários e métricas — documentadas como requisitos antes de qualquer código.
  • Bug encontrado: o agente criou a seção de confirmação com formato errado, entrando em loop infinito no gate. Destravei manualmente depurando o código-fonte do motor e corrigindo o arquivo + registrando o checkpoint via CLI.
  • Kiro ficou sem tokens no meio do code-generation. O workflow foi retomado 100% via CLI do engine (aidlc engine orchestrate next, log review, orchestrate report) — prova de que o estado é realmente portátil.
  • O primeiro plano de código propôs o mesmo visual rejeitado. No gate de aprovação, registrei Request Changes com a direção "claro corporativo", gerei um mockup HTML de preview, o usuário aprovou, e o plano foi revisado antes de uma linha de código ser escrita.
  • Redesign implementado: 12 arquivos, novo design system (indigo #4f46e5, fundo claro, sidebar escura, sem glassmorphism). typecheck e vite build: PASS.
  • Revisão adversarial por subagente: veredito READY, com 1 major (contrato de testes sem runner — aceito conscientemente no gate).
  • Stages concluídos: code-generation e build-and-test (2/10 do pipeline Construction). O estágio ci-pipeline travou num loop de cerimônia (ordem estrita entre confirmação de resumo e escrita auditada de artefatos — depende de hooks do harness).
  • Validação final real: Docker Desktop iniciado via CLI, Postgres healthy, API .NET no ar com login JWT funcionando, frontend servindo em :5173.

4. Acertos e benefícios observados

🧠 Memória real

Regras em camadas (org→time→projeto→fase) versionadas no git, carregadas em todo estágio. Decisões ficam no projeto, não no chat.

🚦 Gates que funcionam

O gate de aprovação de plano salvou o redesign: impediu regenerar o visual errado e canalizou a direção "claro corporativo" antes do código.

📜 Auditoria de verdade

Cada pergunta, resposta, decisão e escrita vira evento no audit shard com receipts verificáveis (hashes, autorizações).

🔄 Estado portátil

O workflow sobreviveu à morte do harness: Kiro sem tokens → continuei pelo motor CLI sem perder nada. Isso é arquitetura, não acidente.

🔍 Review adversarial

Segundo agente revisou o trabalho e achou problemas reais (testes ausentes, contraste WCAG, fonte morta) — decididos no gate, não escondidos.

🗣️ Contexto linguístico

Perguntas, resumos e artefatos gerados em pt-BR corretamente — a memória registra e respeita o idioma da conversa.

6. Veredito

O AI-DLC cumpre a promessa central: transforma o assistente de "gerador de código" em "processo de engenharia". O redesign saiu melhor por causa dos gates — a direção visual errada foi pega no plano, não no código. O preço é fricção: cerimônia rígida, formato de arquivos exigente e dependência dos hooks do harness — quando a cota do Kiro acabou, operar o motor na mão virou trabalho de especialista. Para times que valorizam rastreabilidade e controle (e têm cota de sobra), o modelo é forte. Para uso rápido e casual, a burocracia pesa.
